---
title: Granular updates
description: Partial patches in, partial patches out — no full snapshots.
---

## The principle

`compute()` accepts a partial patch and returns a partial patch. No full-state snapshots cross the API boundary.

```ts
// User edits quantity. You pass only that.
graph.compute({ quantity: 2 });

// Result: { quantity: 2, subtotal: 20, tax: 2, total: 22 }
// Only the four fields that changed.
```

The shape of the patch matches the shape of root state. `Object.assign(state, patch)` merges cleanly — no overwriting unrelated sibling fields.

## Why granular

- **Minimal updates.** Your state manager (Zustand, MobX, React) receives only what changed. It can optimize re-renders and skip diffing.
- **No accidental overwrites.** Deeply nested patches only touch the paths they contain. `Object.assign(state.user, patch.user)` doesn't clobber `state.user.profile` if the patch doesn't include it.
- **Clear call sites.** You don't have to spread the whole form into `compute()`. Pass only the field that changed.

## How patches merge with base state

`compute()` needs to know the current values of fields you didn't pass, so it can run formulas correctly. Two ways to provide them:

### 1. Pass them in

```ts
graph.compute({ ...currentValues, quantity: 2 });
```

Simple, explicit, but requires spreading every time.

### 2. Configure `getState`

```ts
const graph = createGraph<Form>(
  { /* formulas */ },
  { /* sources */ },
  {
    getState: () => store,
  },
);

// The graph reads store at flush time and merges in your patch.
graph.compute({ quantity: 2 });
```

`getState` is called **once per cycle, just before evaluation**. This prevents stale closures when inputs change between `compute()` being called and the microtask flushing.

## Applying patches with `setState`

```ts
const graph = createGraph<Form>(
  { /* formulas */ },
  { /* sources */ },
  {
    getState: () => store,
    setState: (patch) => {
      // patch contains only changed fields in same structure as root
      Object.assign(store, patch);
    },
  },
);

// Fire-and-forget — setState wires the result back into the store
graph.compute({ quantity: 2 });
```

`setState` fires only for non-stale results. If a cycle's result becomes stale (inputs changed during async work), `setState` is not called for it.

## Awaiting the result instead

If you prefer explicit control:

```ts
const result = await graph.compute({ quantity: 2 });
Object.assign(store, result);
```

Both work. Pick the one that matches your store's preferred update style.

## Batching multiple updates

`compute()` calls in the same microtask are coalesced into one cycle.

```ts
graph.compute({ quantity: 5 });
graph.compute({ basePrice: 20 });
graph.compute({ taxRate: 0.1 });
// → one DAG execution
// → setState fires once with the combined patch
```

The merged patch is what reaches `setState` and is what the returned promises resolve to.

## What patches contain

The returned patch contains:

- **Every field you passed in** (echoed back).
- **Every computed field that was evaluated this cycle.**

It does **not** contain:

- Computed fields whose dependencies didn't change.
- Source fields you didn't pass.

This is what "granular" means: the patch is the minimal description of what changed.
